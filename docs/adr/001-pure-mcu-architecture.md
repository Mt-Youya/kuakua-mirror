# ADR 001: 纯 MCU 架构

## 状态
已接受（2026-08-27）

## 背景
项目需要在 3 天内完成 MVP 演示，硬件包含 MCU（带 WiFi/蓝牙/摄像头/麦克风/扬声器）。面临选择：
1. 纯 MCU 方案：ESP32-S3 作为唯一算力主体
2. MCU + 协处理器：增加树莓派/手机/平板处理复杂任务
3. MCU + 云端：所有计算下沉到云端，MCU 只做 I/O

## 决策
采用**纯 MCU 方案**：ESP32-S3 作为唯一算力主体，不增加树莓派、手机或平板。

MCU 职责：
- WiFi 连接后端 WebSocket 服务
- 音频采集和 Opus 编码
- 音频解码和扬声器播放
- 本地人脸检测（控制屏幕待机）
- SPI 屏幕显示对话文字
- 按键检测和状态机管理

云端职责：
- ASR（语音识别）
- 大模型推理
- TTS（语音合成）

## 后果

### 正面
- **成本低**：无需额外硬件（树莓派 ~$35，增加 50% 成本）
- **体积小**：单 MCU 方案便于集成到镜子内部
- **功耗低**：ESP32-S3 待机功耗 <100mW，树莓派 >2W
- **开发简单**：单一固件，无需跨设备通信协议

### 负面
- **算力受限**：无法运行端侧大模型，完全依赖网络
- **功能约束**：人脸识别只能做简单检测（存在感知），无法识别具体身份（除非后续增加云端识别）
- **扩展性差**：若后续需要本地语音唤醒词检测或端侧 LLM，需要硬件升级

### 风险缓解
- 网络依赖：在 WiFi 断开时显示错误提示，引导用户检查网络
- 算力不足：如 3 天内发现 ESP32-S3 无法胜任（音频编码延迟过高、内存溢出），预留"后续看时间来不来得及补"的回退方案（用户在 Q4 回答中提及）

## 替代方案
1. **MCU + 树莓派**：树莓派运行本地 Whisper ASR，减少云端依赖 → 被拒绝（成本和时间）
2. **纯云端方案**：MCU 直接推送 PCM 裸音频到云端 → 被拒绝（带宽占用是 Opus 的 10 倍）
